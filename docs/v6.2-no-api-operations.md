# V6.2 无 API 条件下的运营能力扩展计划

## Context

用户进一步确认一个现实约束：很多商家无法提供淘宝、京东、抖音等平台 API 权限。因此 V6.2 不能把业务能力和平台 API 绑定在一起。需要把“业务域能力”“数据接入方式”“自动执行能力”拆开：没有 API 时仍然建设内部业务模型、权限、审核、异常、导出和审计；通过官方报表、第三方 ERP/API、商家上传、人工录入或合规低频 RPA 降级接入；所有自动平台写操作继续后置。

本计划是对 V6.1 的优化，不是继续无限扩张模块。V6.2 优先补齐日常运营毛细血管：物流事实/异常、轻量客服工单、数据导出、PIM 发布草稿；价格监控和供应商退货/索赔后置。没有 API 时实时性下降，但不能让系统失去业务价值。

## 核心架构决定

### 业务域与数据源解耦

```text
API / 官方报表 / CSV-Excel / 第三方 ERP / 手工模板 / 合规 RPA / replay
                                  ↓
                            Intake Adapter
                                  ↓
                        标准化外部事实层
                                  ↓
                OMS / 物流 / 售后 / PIM / 分析 / 工单
                                  ↓
                       导出、人工处理和审批
```

所有外部事实必须保存：

```text
source_mode: api / csv / manual / erp / rpa / replay
source_batch
observed_at
received_at
data_completeness
simulated
payload_hash
raw_ref
```

没有 API 时，系统可以从实时自动同步降级为准实时或手动导入，但必须显式展示数据延迟、来源和完整度，不得假装实时。

### 接入方式优先级

| 方式 | 适用 | 产品状态 | 边界 |
|---|---|---|---|
| 官方 API | 有授权和测试店铺 | 优先生产接入 | 凭证、scope、限流、停用和审计齐备 |
| 官方报表导出 | 无 API 的主要兜底 | 首选降级方式 | 商家下载/上传，支持 CSV/Excel/JSON，保留来源批次 |
| 第三方 ERP/API | 商家已有 ERP | 可选适配器 | 需要商家授权和供应商契约，不把第三方数据写成平台直连 |
| 合规低频 RPA | 报表无法导出且明确授权 | 实验/受控 | 复用人工登录态，低频、人工触发、限速、可停止，不绕过验证码/MFA/风控 |
| 手工模板/录入 | 最终兜底 | 必须支持 | 适合物流单号、价格快照、供应商和异常处理 |
| 未授权爬虫/绕过风控 | 不适用 | 禁止 | 不抓取非公开经营数据，不破解、不绕过平台限制 |

## V6.2 业务范围与判断

### P0：物流事实与异常告警（纳入）

放在 V6-P3 OMS/履约子域，但第一版不做自动打单。

目标对象：

```text
ShipmentFact
TrackingEvent
DeliveryException
FulfillmentSla
```

第一版：

- 商家导入订单/包裹/快递单号；
- 支持物流 Provider、CSV/Excel 和人工补录；
- 保存轨迹事件、最近状态、观察时间、来源和完整度；
- 识别停滞、拒收、丢件、退回和承诺时效超时；
- 生成异常告警和人工处理任务；
- 客服和 OMS 查询只读物流视图。

API 不可用时的降级：物流单号导入、物流服务商授权接口、低频查询或人工更新。快递查询渠道必须逐家核实授权和数据使用条件，不默认认为存在公开可用 API。

明确不做：自动电子面单、自动下单、自动发货、平台履约写回。

DoD：固定物流事件回放可重建当前状态；重复事件 no-op；异常告警可去重、关闭和审计；数据延迟可见；跨 Workspace 不越权。

### P0：轻量客服工单（纳入）

放在 V6-P10 客服子域，与知识库、会话和售后案件关联。

目标对象：

```text
ServiceTicket
TicketAssignment
TicketEvent
TicketLink
```

状态：

```text
open → assigned → in_progress → waiting_customer/waiting_internal → resolved → closed
```

第一版：

- 手动创建或从客服会话/售后案件创建；
- 分配客服、仓库、财务或运营责任人；
- 备注、内部协作、附件引用、关联订单/SKU/售后案件；
- 状态流转、操作审计和基础 SLA 超时告警；
- AI 只能分类、摘要和建议，不自动关闭或替用户承诺。

没有平台 API 仍可完整运行，因为工单是本系统内部能力。复杂客服渠道接入、自动回复和复杂 SLA 规则后置。

DoD：跨部门责任可追踪；状态、actor、时间、SLA 和关联事实可查；越权、重复、并发冲突和人工接管有测试。

### P0：数据导出（纳入）

放在 V6-P8 经营分析/平台基础能力。

目标对象：

```text
DataExportJob
ExportArtifact
ExportAccessAudit
```

第一版支持：

- 订单、库存、销量、补货、对账、售后和指标的 CSV/JSON 导出；
- 当前 Workspace/仓库权限过滤；
- 异步导出、分页/上限、文件 hash、生成时间、来源和过期时间；
- 下载审计和失败重试；
- 无 API 时作为商家向财务/BI/ERP 传递数据的主要出口。

Webhook、数据订阅和每日自动发送后置到 P6/P11，需先定义事件版本、签名、重试、去重和用户映射。

DoD：大结果集不阻塞请求；导出与 API 指标口径一致；权限、敏感字段和下载审计有测试。

### P1：PIM 发布草稿与人工导出（纳入，自动发布后置）

放在 V6-P7 PIM/AIGC。

第一版：

```text
Product/SKU
→ ChannelFieldMapping
→ ValidationReport
→ PublicationDraft
→ Excel/JSON/图片素材包导出
→ 人工在平台后台发布
```

实现：

- 淘宝/京东/抖音等渠道字段映射配置；
- 标题长度、必填属性、枚举、单位、敏感词和 claims 检查；
- 内容 revision、人工审核、版本、导出 manifest；
- 导出明确标记 `simulated/manual_publish`。

没有 API 时仍然有价值：系统负责事实、内容、校验和素材包，商家负责平台后台最终发布。官方 API 发布必须另建 ChannelPublicationJob、授权、任务队列、失败重试和回滚门禁，不在第一版实现。

### P1：只读价格快照与告警（条件纳入）

放在 V6-P8，但仅在有真实业务需求和合规数据源时启动。

第一版：

- 自有商品多平台价格快照；
- 商家 CSV/Excel/手工导入；
- 授权 ERP/数据源适配；
- 价格历史、变化告警和最低限价规则 proposal。

竞品价格监控必须确认平台规则、数据公开性和授权；不做大规模高频采集。绝不自动改价、自动发布或绕过风控。

### P2：供应商退货与索赔（后置）

放在 V6-P9 SCM/SRM，只有真实供应商流程需求时启动。

目标对象：

```text
SupplierReturnOrder
SupplierClaim
SupplierReplacement
```

第一版做采购退货、少发/损坏/不良品证据、索赔金额草稿、换货/补发状态和人工确认；不自动供应商下单、付款或生产系统写入。

## 不因无 API 而取消的能力

以下能力主要是本系统内部业务能力，不依赖平台 API：

```text
轻量客服工单
数据导出
售后案件与库存处置 proposal
PIM 属性/内容/校验/人工发布草稿
供应商退货/索赔内部流程
物流异常管理（只要有单号或导入事实）
```

## 没有 API 时必须降级的能力

```text
实时订单/物流同步 → 报表或模板导入
自动物流轨迹 → 低频授权查询/人工更新
平台商品自动发布 → 发布草稿/Excel/JSON 导出
竞品价格自动监控 → 手工/授权数据源快照
Webhook 实时推送 → CSV/JSON 导出
```

## V6.2 推荐执行顺序

```text
V6.2-P0 多数据源 Intake Adapter 契约与元数据
  ↓
V6.2-P1 物流事实、TrackingEvent、异常告警
  ↓
V6.2-P2 轻量 ServiceTicket 与责任流转
  ↓
V6.2-P3 DataExportJob、CSV/JSON 导出和下载审计
  ↓
V6.2-P4 PIM PublicationDraft 与人工发布导出
  ↓
V6.2-P5 条件性价格快照/告警
  ↓
V6.2-P6 条件性供应商退货/索赔
  ↓
V6.2-P7 Webhook/订阅/真实平台发布（授权后）
```

## V6.2 共同门禁

- 每个接入事实带 `source_mode/source_batch/observed_at/received_at/data_completeness/payload_hash`；
- API、CSV、ERP、RPA、manual、replay 归一到同一标准化事实，不让上层业务感知 transport 细节；
- 没有实时数据时明确展示延迟和完整度；
- RPA 只允许明确授权、低频、人工触发、可停止和可审计，不绕过验证码、MFA、风控或访问限制；
- 所有平台写操作（打单、发货、发布、改价、退款、Webhook）单独审批、幂等、停止、重试和补偿；
- fixture/mock/人工录入只能证明流程和数据契约，不证明平台生产接入或实时性；
- 先做领域事实和内部工作流，再决定是否投资具体平台 Adapter。

## 验收标准

- 无 API 的商家可以通过 CSV/Excel/模板完成核心工作流；
- 同一个业务事实可由 API、报表、ERP、manual 或 replay 导入且上层响应一致；
- 来源、延迟、完整度和模拟标记可查询；
- 工单、物流异常、导出和发布草稿均可人工接管；
- 不执行任何未授权的平台写操作；
- 跨 Workspace、重复导入、冲突、部分失败、取消、下载权限和审计均有测试。
