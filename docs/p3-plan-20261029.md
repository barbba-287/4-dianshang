## 0. 核心判断（先看这个）

**P3 不是"从零建采购与入库"——入库与入账中台已经存在且已测过。**

仓库事实：`InboundOrder`（实收单）+ `InboundLine`（行级 expected/received/damaged）+ `InventoryTransaction`
（行级幂等流水）+ `InventoryBalance`（余额）+ 前端 `warehouse.html` 实收页 **全部已实现**，
`POST /api/inbounds/{id}/confirm` 就是"运营确认入账"（写流水 + 累加余额）。

**真正缺的是两样**：① 采购申请的**审批环节**（现在是 draft→submitted 就断了）；
② 采购申请与入库单的**关联**（全仓 grep `purchase_request_id` 在入库侧**零命中**）。
P3 的主体工作量是"接桥 + 审批 + 一致性校验"，不是重建库存体系。

## 2. 关键发现（影响 P3 设计的 5 条）

1. **入账中台已存在**：确认入账 = 写 `InventoryTransaction`（幂等键幂等）+ 改 `InventoryBalance`。P3 **不得**新建第二套入账逻辑，否则两套账并行必出对不平。
2. **采购申请已有幂等骨架**：`PurchaseRequestAction` 的 `(workspace_id, purchase_request_id, action_type, idempotency_key)` 唯一约束 + `expected_version` 乐观锁，审批动作可直接复用，不必新造审计表。
3. **入库单只支持单 SKU 行一次收货**：`InboundLine` 唯一约束 `(inbound_order_id, sku_id)` → 同单同 SKU 不能分两次收。**分批到货需多张入库单**（P3 设计按此约束，不擅自改约束）。
4. **`InventoryTransaction.movement_type` 目前实际只写一种值**：`inbound_confirm`（列默认 `inbound` 但代码未用）。无出库/调拨/盘盈亏——P3 只做入库，出库留给 P4。
5. **前端缺口与后端能力严重不匹配**：采购、内容、订单三条能力都只有 API 没有页面；而 P3 验收如果只看 pytest，会再次产出"能力真、不可用"的状态。**P3 每切片必须带最小页面**。

## 4. 三个切片拆解

### 切片 S1：采购单与审批（P0，最高优）

**目标**：申请 → 提交 → 审批（通过/驳回）→ 生成待收货入库单，全链路留痕、幂等、可追溯。

**表设计评估（结论：不新建 `PurchaseOrder`，扩展 `PurchaseRequest`）**

| 方案 | 内容 | 评价 |
|---|---|---|
| A（推荐） | `purchase_requests` 加审批列（`approved_by/approved_at/approved_note/rejected_by/rejected_at/reject_reason`）；status 扩为 `draft → submitted → approved｜rejected` | 一张表一条链，审计走既有 `PurchaseRequestAction`；避免 Request/Order 双表状态双写 |
| B | 新建 `PurchaseOrder` + `PurchaseOrderLine`，审批通过时复制 | 三条数据链（Request→Order→Inbound）对账复杂、幂等要点翻倍；现有 `InboundOrder` 已能承接，无收益 |

**若用户坚持"申请与采购单是两个实体"**（如未来要一申请拆多单），则选 B，但需追加"拆分/合并"规则与独立幂等键——建议留到真实需求出现时再做。

**改动面（方案 A）**：
- `db.py`：`PurchaseRequest` 加 6 列（全 nullable）；`status` 语义扩展（字符串列，无需 migration 改类型）
- `replenishment.py`：`approve_purchase_request()` / `reject_purchase_request()`（状态机 + 乐观锁 + `PurchaseRequestAction` 落审计）
- `main.py`：`POST /api/purchase-requests/{id}/approve`、`POST /api/purchase-requests/{id}/reject`（权限 `purchasing.approve`，**需确认角色体系是否已有该权限——见 §10 Unknown U2**）
- `main.py`：`POST /api/purchase-requests/{id}/inbound-orders`（按未收数量生成 `InboundOrder` + `InboundLine`，status=expected，`reference_no` 以采购单号派生）
- `schemas.py`：响应加审批三键（只增不改）
- `templates/purchase.html` + 页面路由：列表 / 详情 / 审批按钮 / 生成入库单
- migration 0023（加列，down 逐列还原 0022 形态）

**状态机（写死候选，待任务文件确认）**：
```
draft ─submit─▶ submitted ─approve─▶ approved ─(收货进度由入库单聚合，不改 PR 状态)─▶ closed
                     └─reject──▶ rejected ─(可重新编辑)─▶ draft
```
**关键决策**：**采购单状态不由入库单反写**（避免双写与死锁），"已收多少 / 是否收齐"用聚合查询（`SUM(inbound_lines.received_qty) WHERE purchase_request_id=?`）派生。验收时以聚合值断言，不以 PR.status 断言。

**测试要点**：审批幂等（同 key 同结果）、乐观锁版本冲突 409、越权（非审批权限 403、跨 workspace 404）、非法状态迁移 409、驳回后可重提、生成入库单的行数/数量与未收量一致、生成幂等（重复调用不产生第二张单）。

**验收**：全量 435+N / 0；定向 ≥10 例；最小页面可完成"提交→审批→生成入库单"三步。

### 切片 S2：采购 → 实收 → 入账闭环（P1）

**目标**：入库单显示采购来源；实收数量与采购未收量校验；确认入账后采购进度可见。

**表设计评估（结论：不新建 `GoodsReceipt`，给 `InboundOrder` 加关联列）**

| 方案 | 内容 | 评价 |
|---|---|---|
| A（推荐） | `inbound_orders` 加 `purchase_request_id`（FK nullable, index）；`inbound_lines` 加 `purchase_request_line_id`（FK nullable） | 一处关联、入账逻辑零改动（`inbound_confirm` 复用）；历史手工入库单保持 NULL 可用 |
| B | 新建 `GoodsReceipt` 表与 `InboundOrder` 并存 | 与 `InboundOrder` 语义重叠，等于复制已测过的实收+入账链路，明确不做 |

**改动面（方案 A）**：
- migration 0024（两列 + 索引，down 还原）
- `repository.py`：`create_inbound` 支持写入关联；`receive` 增加校验——① 行必须属关联采购单；② `received_qty + damaged_qty` 超未收量 → 409 `INBOUND_OVER_RECEIVE`（MVP 不做超收放行开关）；③ 采购单未 approved → 409 `PURCHASE_REQUEST_NOT_APPROVED`
- `main.py`：`GET /api/inbounds?purchase_request_id=` 过滤；入库详情响应带采购来源三键（只增不改）
- `templates/warehouse.html`：实收页显示来源采购单/供应商/到货日期与"剩余未收"
- 新增只读视图：`GET /api/purchase-requests/{id}/receipt-progress`（聚合汇总，避免前端算账）

**关键约束（写死）**：**入账永远只经 `confirm`**；外部平台快照绝不写 `InventoryBalance`（架构铁律，S2 加一条防漂移测试：`grep` 断言 `InventoryBalance` 写入点仅 `repository.py` 入账路径）。

**测试要点**：关联建单、超收 409、未审批采购单建单 409、跨采购单行混入 409、部分收货后剩余量正确、确认入账后 `on_hand_qty` 增量 == Σ(received−damaged)、重复 confirm 幂等不重复加库存、无关联历史单不受影响。

**验收**：全量 +N / 0；端到端演练（申请→审批→入库→实收→确认→库存增加）一次跑通并留证。

## 6. 边界与红线（P3 全程有效）

1. **外部事实与内部账本分离**：`InventoryBalance` 唯一写入点是确认入账；任何外部快照/同步路径不得触碰（S2 加防漂移测试）。
2. **proposal-only**：审批只是内部留痕，**不发单给供应商、不对接采购系统**；无自动下单/付款/改价。
3. **缺数据不硬给结论**：采购数量不足、未收量未知 → 返回 `unknown/insufficient` 语义（沿用补货域既有 `data_completeness` 先例）。
4. **不做**：出库/调拨/盘盈亏（P4）、多仓库调拨、供应商主数据管理、超收放行、发票与对账。
5. **串行实施**：S1 → S2 → S3，严禁并行（都动 `db.py`、`replenishment.py`、`main.py`、migration head）。
6. **live 无关**：P3 三切片全部 offline/mock 可验，不需要 live 验证，也不得开 `.env` 的 live 基线。
