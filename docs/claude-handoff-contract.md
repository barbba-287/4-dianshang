# Claude Code 任务交付契约

- 版本：v1
- 生效日期：2026-10-11
- 状态：生效（需在 `CLAUDE.md` 登记后对 Claude Code 生效）
- 适用对象：`D:\ai\dianshang`（电商 AI 长期开发计划，当前 V6.2）
- 上位依据：`CLAUDE.md`（项目开发执行规范）、`docs/engineering-roadmap.md`（工程长期路线）

## 1. 目的与适用边界

本契约定义**规划方**（产出任务文件的一方）与**实现方**（Claude Code）之间的交接格式与证据要求，解决的问题是：**实现方同时编写代码、编写自己的测试、报告自己的结果，导致"测试通过"无法自证。**

本契约只规范交接与举证，**不替代** `CLAUDE.md` 的完成前门禁，也不改变任何业务语义、接口契约或权限模型。两者冲突时以 `CLAUDE.md` 为准。

## 2. 角色与职责

| 角色 | 职责 | 明确不承担 |
|---|---|---|
| 规划方 | 现状基线核查、需求拆解、范围与非范围定义、接口契约、测试用例设计、交付独立复核 | 不写业务实现代码 |
| 实现方（Claude Code） | 按任务文件实现、编写测试、提供可复现证据 | **不得自证验收**；不得自行扩大范围 |
| 用户 | 范围拍板、权限授权、分支推进与提交 | — |

## 3. 任务下发格式

### 3.1 位置与命名

- 单任务：`dev_task.md`（仓库根目录）
- 多任务并行：`dev_task.<slice-id>.md`（如 `dev_task.p1-content-export.md`）
- 任务文件**必须纳入版本控制**，不得加入 `.gitignore`（见 §6.1）

### 3.2 必需章节

任务文件必须包含以下九个章节，缺一即视为无效任务：

```text
# 任务                  → 任务标题 / 任务目标 / 选择理由
## 当前事实              → 已实现内容 / 当前未提交改动 / 相关文件 / Fact-Target-Assumption-Unknown
## 本次范围              → 允许修改的文件 / 不允许修改的文件 / 明确不做的事情
## 实施要求              → 数据流与状态边界 / Workspace-RBAC 边界 / 幂等-版本-事务-审计 / 失败-重试-取消-人工接管
## 验证命令              → 定向测试 + 必要的全量测试（可直接复制执行）
## 完成标准              → 正向 / 负向 / 越权 / 重复幂等 / 故障回放 / 真实-模拟-未知区分
## 禁止操作              → reset / clean / 删除未跟踪文件 / commit / push / 任意外部平台写入
```

参考样例：`dev_task.md`（P1 内容导出切片，2026-10-10）。

### 3.3 事实标注纪律

`当前事实` 章节中的每条陈述必须可追溯到**文件路径 + 行号**或**已执行的命令**。禁止写入：

- 未标注来源的测试数字（如"历史上 205 passed"）
- 把 `mock`/`fixture`/`local` Provider 描述为生产能力
- 把 `Unknown` 项写成已完成

## 4. 交付格式（实现方必须遵守）

### 4.1 交付说明必需字段

| 字段 | 要求 | 缺失后果 |
|---|---|---|
| 改动文件清单 | 每个文件 + 改动性质 + `sha256` 前 16 位 | 无法确认验的是哪一版 |
| 未改动声明 | 显式列出声明"未改动"的文件 | 声明不可核验 |
| **原始测试输出** | 完整命令 + 原始 stdout（含 `passed`/`failed`/`error` 行） | **不得标记完成**（见 §4.3） |
| 逐条用例映射 | 任务文件用例编号（P1/N1/A1/R1/F1…）→ 测试函数名 | 无法判断覆盖是否达标 |
| 真实 / 模拟 / 未知边界 | 三段式说明 | 见 `CLAUDE.md` 完成前门禁 |
| 已知限制 | 未覆盖项与原因 | — |

### 4.2 测试证据规范

```bash
# 必须原样输出命令与结果，禁止只写结论
cd D:/ai/dianshang && PYTHONDONTWRITEBYTECODE=1 python -m pytest -q -p no:cacheprovider <targets>
```

若使用隔离临时目录（推荐，避免污染系统 temp）：

```bash
cd D:/ai/dianshang && PYTHONDONTWRITEBYTECODE=1 python -m pytest -q -p no:cacheprovider --basetemp=D:/ai/dianshang/.testtmp
```

### 4.3 禁止自称"完成"的情形（硬门禁）

以下任一情形成立，状态只能写 **进行中 / 待验收 / 可演示（模拟） / 待授权 / 未知**：

| 编号 | 情形 |
|---|---|
| H1 | 无原始测试输出，只有汇总数字或结论 |
| H2 | 测试数字与命令、日期、环境不可对应（如引用历史数字） |
| H3 | 声明"保持字节不变"但文件出现在 `git status` 的改动列表中 |
| H4 | 删改/覆盖了任务文件未列入范围的既有测试或既有文件 |
| H5 | 新增测试的断言路径不可达（见 §5.1） |
| H6 | 关键结论依赖并发、锁、事务等**未经独立复现**的行为 |
| H7 | 存在未披露的范围外改动（含误改、顺手清理） |

### 4.4 与原基线的关系必须说清

"基线"指**本次改动开始前**的实测结果。禁止把下列内容当作基线：

- 本次新建文件产生的失败或错误
- 历史文档中的数字（如 `docs/p0-0-release-review.md` 记录的 205 passed）

格式要求：`改动前 <N> passed / <M> failed（<命令>，<日期>）→ 改动后 <N'> passed / <M'> failed`。

## 5. 复核方（独立验收）的检查项

### 5.1 测试有效性检查（针对 H5）

对新增测试必须确认：断言路径在真实调用链上**可达**。检查方法：

1. 读被测代码，确认被 monkeypatch 的函数在目标分支上是否真的会被调用；
2. 若断言的是异常类型，确认该异常在真实约束/真实依赖下会从该位置抛出；
3. 关键路径用**独立探针脚本**复现（不改动仓库），而非依赖被测方自己的测试。

### 5.2 并发与幂等结论的独立复现（针对 H6）

并发、唯一约束、锁相关结论，必须有独立复现证据才可采信。检查方法：

1. 用真实数据库（本地可用 SQLite）构造真实约束冲突；
2. 确认冲突抛出的**位置**与代码捕获的 `try` 范围一致；
3. 确认失败时的对外表现（HTTP 状态码、错误码）符合任务文件的稳定错误语义要求。

### 5.3 范围与禁止清单核对

```bash
cd D:/ai/dianshang && git status --short
```

逐项比对：`本次范围` 允许清单 / 不允许清单 / `禁止操作` 清单。

### 5.4 复核结论格式

```text
结论：通过 / 不通过 / 有保留通过
- 已独立核验：<项>（<依据>）
- 未独立核验：<项>（<原因，如权限受限>）
- 需修订：<P0/P1/P2 问题 + 最小修订动作>
```

**未独立核验项必须显式列出**，不得与已核验项混写为"全部通过"。

## 6. 环境与工具约定

### 6.1 任务文件的版本控制

任务文件与契约文件应与代码同版本推进。分支推进顺序遵循 `CLAUDE.md`：`develop → staging → temp-prod → main`。

### 6.2 临时目录与产物隔离

| 场景 | 约定 |
|---|---|
| pytest 临时目录 | 优先 `--basetemp=D:/ai/dianshang/.testtmp`，避免系统 temp 清理引发授权拦截 |
| 运行产物 | `artifacts/`（已在 `.gitignore`） |
| 探针脚本 | 不得写入仓库；放在仓库外的临时位置，只读访问仓库 |
| 演示数据库 | `data/*.db`（已在 `.gitignore`） |

> 环境限制：若运行环境存在 `sitecustomize.py` 之类的 shim 劫持 `shutil.rmtree`（回收站删除被阻止），
> `--basetemp` 的 fixture teardown 清理阶段会报 error（非断言失败），表现为全量 `errors` 而非 `passed/failed`。
> 此时应在无 shim 环境复跑，或临时移除 shim 后重跑；勿将此类清理阶段 error 误判为测试失败。

### 6.3 解释器

项目解释器：`D:\python\python\python.exe`（Python 3.14.4，fastapi 0.141.1，pytest 8.4.2）。
`tests/conftest.py` 会强制覆盖 `DATABASE_URL` 为 SQLite、`EMPLOYEE_AUTH_ENABLED=false`；需要真实鉴权的 API 测试须在 fixture 内显式开启员工鉴权并按范式登录（参考 `tests/test_api_analytics.py:12-56`）。

## 7. 缺陷分级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 功能缺陷 / 安全或租户边界问题 / 数据一致性风险 | 必须修复后才可推进 |
| P1 | 范围违规、既有测试或覆盖被删除、硬门禁未过却标记完成 | 修复并披露后才能推进 |
| P2 | 报告准确性（基线、字节不变、warnings 归属） | 修正表述 |
| P3 | 契约一致性建议（错误码映射、返回结构、失败回滚） | 记录，可后续任务处理 |

历史案例（2026-10-11 P1 内容导出切片）：P0 = 并发兜底位置错误（`IntegrityError` 在 `flush()` 抛出但 `try` 只包住 `enqueue_job`，真实竞态下 500，且三个对应测试断言的是不可达路径）；P1 = 原有 `test_review_requires_idempotency_key_before_mutation` 被删除导致 `review_revision` 零覆盖。
